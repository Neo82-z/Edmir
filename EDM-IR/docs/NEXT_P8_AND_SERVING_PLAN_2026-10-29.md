# 下一轮 P8 与 serving 衔接方案

日期：2026-10-29。状态：讨论稿，尚未封存或执行。没有启动 GPU、租机、改评分权重或改六形状协议。本文件不把旧 D7 的范围扩展成已完成的 serving 实验。

同日补充：按用户提出的 CPU 预准备、多家模型候选与 H100 一/四卡资源条件，参见 [CPU 准备与硬件一致性](CPU_PREPARATION_AND_HARDWARE_SCOPE_2026-10-29.md)。本文件的“仅准备一个 Qwen 模型”调整为候选资产池，正式测量仍按阶段收敛；P8 验证及冻结六形状没有改成 H100/P4。

## 1. 本轮要交付什么

下一次八卡窗口交付两件东西：**同身份的 P8 候选对照与少量机制观测；一个原生 BF16 MoE 的可运行基线、真实路由和阶段耗时记录。** 八卡模型独立验收以及接入本方法后的 serving 收益另有明确门槛，不能用“API 能回复”代替。

当前状态：

| 证据 | 已知结果 | 边界 |
| --- | --- | --- |
| P4 FP16 开发回放 | 保留模型 3/41 误选，平均/最坏选择损失 0.0802%/1.5801% | 已反复参与设计；不是 P8/BF16 独立成绩 |
| P4 全 M512 留出 | 一次 host/fused 误选，最坏损失 7.3566% | 比三个短 K 小错误更值得检查 |
| 已有 P8 GPU 记录 | 四个开发形状、22 配置、三次进程重复；20 配置有效 | 子集测量；部分 q16 数值失败；执行身份不同 |
| 六形状 | 已冻结，未采集/评分 | 必须先固定可评价的 P8 policy，不能用来补训练覆盖 |
| 真实 MoE | CPU 路由契约、参考和统计接口已有 | 引擎版本、真实 hook、GPU routed BF16 接口及实际 trace 仍缺 |

近几轮本地依赖和缓存分析支持收敛：纯粹继续细分固定 CTA 服务不能解释短 K 的反转；模拟输出不能替代实际资源服务。旧数据零误选不再作为继续无限迭代的理由，原冻结评价仍保留误选数及所有失败。

## 2. 一个统一的研究问题

对于给定输入、路由、精度、实现和拓扑，在数值合格的候选中选择完整执行边界内耗时较低的方案：

`c* = argmin[c in C_valid(x,e)] T_hat_complete(x,c;e)`

这里的完整耗时由依赖图和共享资源共同决定，不能把 CPU、通信、计算区间直接相加。三类量必须分开：

1. 可核算工作：有效/重放字节、tile/CTA、K 分片、输出更新和依赖边。
2. 条件服务：实际驻留、可发射 warp、通信队列、缓存状态、远端源争用及流水线等待。
3. 最终观测：整个算子或请求从入口到完成的时间，包含该边界要求的准备、转换与同步。

评价先看实际选择损失，耗时误差和排序正确率同时报告。当前参考最优均是“已测有效候选中的最优”，不是所有实现的理论最优。

## 3. 如何借鉴已有研究

**苏剑林：先检查问题是否被数据约束，再讨论优化器。** 结合此前已完成的原文审查，参数化/有效步长不能只看相同名义学习率；Muon 的适用性也不能替代外推证据。现有 P8 曾出现训练几乎精确、留出 q2 无训练覆盖的情况，增大网络并不能消除这种不可辨识性。下一轮八卡用于补同身份事实；若需要训练，数据回来后在本地完成，矩阵 Muon/AdamW 对照固定结构、划分和预算。耗时回归与决策分数分开解释，不把 softmax 权重叫作真实最优概率。

参考：[11985](https://spaces.ac.cn/archives/11985)、[11964](https://spaces.ac.cn/archives/11964)、[已有完整阅读与本地证据](../../experiments/2026-10-28-muon-model-audit/README.md)。本次网页抓取仍为 403/不可达，沿用此前原文阅读记录，未把搜索摘要当全文。

**NVIDIA：先看执行时间线，再收集少量对应计数器。** Nsight Systems 的有限窗口用于 CPU 提交、GPU kernel 和依赖关系；Nsight Compute 仅用于少量可安全独立分析的 kernel。NCU 默认可能串行化 kernel、刷新缓存、控制频率，不能把其结果当作原始 overlap 性能。多 GPU、通信依赖 kernel 不直接套普通逐 kernel replay；不支持的计数器记 unavailable。

参考：[Nsight Systems focused profiling](https://docs.nvidia.com/nsight-systems/UserGuide/index.html#focused-profiling)、[Nsight Compute workload durations](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#workload-durations)。

**DeepSeek：明确 workload 和完整计时口径。** 借鉴 DeepInfer 的预热、prefill/decode 分开和 profiling 分离；保留全部正式计时区间，实际输出 token 才计入吞吐。原文中的满接受 speculative 计数、强制路由和过滤统计区间不能直接搬来作为本项目成绩。当前 DeepEP 主分支还明确要求 Hopper 或更新架构；A100 不承诺使用该实现。借鉴资源预算和通信接口设计，不迁移其硬件数字。

参考：[固定 DeepInfer benchmark](https://github.com/deepseek-ai/DeepInfer/blob/774ce244b87cc0eb8d4b94ab9f5de2ab22049f01/examples/README.md)、[本地源码审查](../../experiments/2026-10-20-deepinfer-measurement-audit/README.md)、[DeepEP 当前要求](https://github.com/deepseek-ai/DeepEP#requirements)。

## 4. 开机前必须完成的工程准备

### 4.1 固定一个执行身份

- 单机 8×A100 SXM4 80GB，同一 NVLink/NVSwitch 域；实际 GPU UUID、拓扑和 P2P 矩阵留档。
- CUDA/NCCL/CUTLASS、编译器、库加载路径及 binary 哈希固定。版本兼容由镜像构建和 smoke 确认，不在付费节点临时升级一串依赖。
- operator FP16 与 native MoE BF16 分开记录；FP32 累加不代表中间写回也是 FP32。
- q16 的已知数值失败保留。不能训练成“很慢”，也不能通过放宽容差把失败变成有效样本。
- 主机预处理和依赖策略对 host/fused 对齐。新环境或 harness 语义变更使用新身份，旧行不得改名混入。

### 4.2 先消除重复启动成本

旧记录每个候选进程初始化/清理常需十余秒，计时本身反而很短。准备“同一形状内多候选、形状/轮次之间独立进程”的运行器：

- 四形状、每形状九候选、三个轮次，108 个测量块，目标 12 次进程初始化；旧方式需要 108 次。
- 每候选输入与输出校验、预热和计时保留。只将一次性的静态 metadata/communicator 初始化按已声明边界放在计时外并单独记录；每次调用必需的 metadata 生成、转换与同步仍按各自契约计入，真实 routed 路径尤其不能把这部分隐藏。
- 三轮使用预先固定的候选位置轮换/随机种子；不能称为覆盖了九个全部位置。预热和缓存状态规则一致。
- 所有候选次序、原始样本、错误和未完成原因都写盘；一个候选数值失败不抹去它的记录。
- 新运行器必须先通过 CPU 契约与超时/断点演练；GPU smoke 后才可采正式样本。复用进程是否改变缓存/温度条件也需记录，不能假定等同历史进程隔离数据。

这是待实施项，当前封存包还不是这个多候选运行器。

### 4.3 模型和引擎资产提前放好

优先沿用 Qwen3-Next-80B-A3B-Instruct，模型 revision 为 `9c7f2fbe84465e40164a94cc16cd30b6999b0cc7`。现有清单记录 checkpoint 约 162.65 GB；应在无 GPU 的准备环境把权重、tokenizer、镜像/依赖和请求语料准备到可挂载存储，校验完整性。无 GPU 准备不等于存储和传输免费，本文件不授权购买。

引擎以固定版本 vLLM 为首选，EP8、BF16；优先核对 TP1/attention-DP8/EP8 的实际通信组，不能把八个独立副本写成 EP8。官方 recipe 支持该模型在 A100 上部署，但其 TP 示例不能直接证明我们的 EP8 配置已通过。通信后端选目标版本实际支持 A100 的 NCCL 路径，不能静默切换到新 DeepEP/DeepGEMM。

首轮关闭 speculative decoding，使用自然 router、固定 expert placement；prefix cache 和 EPLB 的配置明确冻结。诊断 hook 单独开关，不进入正式吞吐进程。是否使用 CUDA Graph/编译模式按可运行配置固定，不能基线关闭、优化组开启后把全部收益归给本方法。

参考：[vLLM Qwen3-Next recipe](https://github.com/vllm-project/recipes/blob/main/Qwen/Qwen3-Next.md)、[EP 配置与通信后端](https://docs.vllm.ai/en/v0.20.1/serving/expert_parallel_deployment/)。所引版本是参考；最终引擎 commit、镜像 digest、启动命令和实际分组仍需绑定。

## 5. 下一轮八卡的最小矩阵

### A. 同身份 P8 开发数据

保留原四形状，不扩展形状网格。每形状的九个诊断候选建议为：

- 逐源 CUTLASS host：机制对照。
- 合并 cuBLASLt host：当前已有的强策略基线，算法选择/workspace 记录。
- direct/g1。
- q2/q4/q8 × g1/g2。

合计 36 配置、三轮 108 个测量块。这里是明示的诊断子集，不是冻结协议的 13 候选完整 oracle；未列入的 direct/g2、其他 host 和 q16 不能被记成已评估。该矩阵补 q2 覆盖并保留 grouped 四格，不能用四个形状宣称广泛泛化。

优先顺序在采集前固定：grouped 形状、M512、其余两点。每个形状优先完成整套候选/重复，不能按已见速度追加有利点。数值失败候选保留，耗时标签为 null。

正式主指标仍是完整算子边界的无 profiler wall-time。分进程/轮次保存数据，再报告硬选择损失、host/fused 双向错误、三轮差值与漂移。不能把同进程 300 次计时当作 300 个独立实验。

### B. 最少的争用与执行条件诊断

只选原 grouped 形状，围绕 q8/g1、q8/g2 做目标 rank 固定工作量的对照：

| 对照 | 保持什么 | 改变什么 | 能回答什么 |
| --- | --- | --- | --- |
| 仅目标目的 rank 工作 / 八个目的 rank 都工作 | 目标 rank 的输入、权重、q/g、源集合及操作数 | 其他目的 rank 的计算与远端读取活动 | 目标 GPU 的同一工作是否受共享资源争用影响 |
| 本地物化输入 / 远端读取输入 | 目标 GEMM 数学、精度与模板 | 输入所在路径；物化路径须另计 copy 与同步 | 远端服务是否改变主循环；不能单独定量证明 overlap 收益 |
| 无 profiler 主运行 / 有限窗口 trace | 配置及输入 | 观测工具 | CPU 提交空隙、事件等待与 kernel 分布；trace 不提供主成绩 |

先完成普通 trace。NCU 只针对不依赖跨设备并发推进的独立计算控制，最多少数 kernel/sections；不收全量 `--set full`，不尝试通过串行 replay 测多卡 overlap。

所需最小证据：实际 grid/block、寄存器、静态/动态共享内存及可运行资源信息；CPU submit/sync、目标 GPU 起止区间、kernel/stream/event 时间线；允许时再取 Tensor/SM 活跃、L2/DRAM 与 stall 信息。指令计数或总流量不能直接当作等待时间；跨 GPU event 不能直接相减。

这些控制尚须本地实现与数值核验。若缺少保持语义的 overlap 开关，论文只声明资源约束下的整体策略收益，不把 timeline 上的重合面积称为消除的通信成本。

### C. 原生 MoE 基线与真实路由

一个模型、一个引擎、两类请求即可。建议准备固定真实文本请求集：较长输入/短输出与较短输入/长输出。具体 token 长度和并发在封存前确认，初始设计可用约 2048/128、256/512，分别配并发 8/32；实际 token、batch 和每步工作量全部记录，不把客户端并发当作专家 M。

采集分两次模式：无 hook 的基线吞吐/请求时间；另一个短诊断进程记录真实 router。

- 每类负载前 3 个完整 prefill 和前 3 个完整 decode step，全部 MoE 层、所有 EP 来源 rank；空 rank/expert 也登记，层/步 ID 必须全局一致。
- 记录专家分配、逐源 bucket、合并专家 M、实际 padded kernel M、投影 K/N、频率与偏斜。检查路由总数等于有效 token×top-k，不允许丢 token。
- 另固定一层、每 phase 一个 step 保存小份激活与完整路由/逆映射，权重通过模型 revision 索引，供随后 routed replay；大小上限提前定，超限保留缺失原因，不悄悄截断成“完整 trace”。
- 正式性能记录完整运行耗时和实际生成 token；TTFT、ITL/TPOT、吞吐和峰值显存先作基线描述，小样本不声称服务 p99 可靠。

Qwen3-Next 的逻辑 hidden=2048、expert intermediate=512。因此在不切分专家投影维度的约定下，gate/up 融合投影约为 `(M,2048,1024)`，down 为 `(M,512,2048)`；实际后端布局和分片必须从引擎核对。这与原四点 K4096/8192 不完全对应，必须先测覆盖，不能默认旧形状代表真实 MoE。

均匀路由下专家平均行数仅为 `T_global×10/512`。例如同一步 128 个全局 token 时约为 2.5 行；这是期望值，不是实际路由或并发换算公式。记录真实分布后，才能决定重点是低 M、prefill 或其他区域。

## 6. 一小时窗口及停止规则

以下是资产齐备、多候选运行器完成后的目标分配，不是当前包已能保证的耗时：

| 计费开始后的时间 | 工作 | 必须带走的结果 |
| --- | --- | --- |
| 0–5 分钟 | 拓扑/环境、构建凭据、正确性与计时 smoke | 是否适合继续、每阶段预计成本 |
| 5–23 分钟 | P8 四形状候选块 | 完整完成的形状及所有失败/未完成标记 |
| 23–29 分钟 | 有限机制 trace | 同身份时间线和可用资源信息 |
| 29–50 分钟 | 模型加载、预热、两类基线请求与短路由诊断 | 原生 MoE 能运行及真实分布；若来不及，保留已完成证据 |
| 50–60 分钟 | 完成回收、逐文件哈希、停止实例 | 本地可读原始记录与实际平台停止状态 |

模型加载/JIT 可能超出这个分配。CPU 可以先完成下载、依赖构建和配置检查，但不能保证所有 GPU JIT 已完成。第 5 分钟用实测启动/预热成本重算；优先删可选计数器与重复诊断，不临时重训或扩充形状。若核心启动已经失败，保存日志结束，回本地修复，不现场消耗完整小时 debug。

预算暂按此前 $15、≤1 小时作设计上限，开机前核实当时 GPU/磁盘单价与可用预算；本文件不产生租机授权或订单。结果持续回收，不能等关机前才开始下载。采集超时或 OS 停止并不等于平台停止计费，须有平台停机保护与最终状态核验。

## 7. 独立评价、训练和 serving 的准入顺序

六形状继续封存。本轮获得新的 P8 同身份开发数据后，在本地检查候选覆盖、可辨识性与 held-out 开发切分；决定一个 P8 policy，冻结模型/源码/环境合同和候选清单，然后才运行六形状独立评价。不能一边看六点结果一边改模型。若没有双向 host/fused 胜负就保留覆盖不足，不能替换六点。

独立评价沿用原协议的平均/最坏选择损失 ≤1%/≤3%，同时检查相对固定策略和强 host 控制、top-k、搜索与决策成本，不要求零误选。若更改协议，单独版本化说明，不能事后宣布新阈值原本就存在。六点是小范围边界验证，不是广泛泛化证明。

serving 分三步，前两步不必等所有预测错误消失：

1. **原生服务可运行**：BF16 模型、EP8、固定请求和性能记录。本轮争取完成。
2. **真实 routed 子图可替换**：实际路由回放正确；实现 BF16 GPU 后端，计入 permutation/metadata/sync/逆变换；与引擎实际使用的强 MoE 后端比较。当前 CPU 参考通过和 FP16 uniform 性能不能跳过这一步。
3. **接回同一引擎做 A/B**：只替换声明的子图，比较固定策略、模型选择和同预算调优；计入选择开销、冷/热缓存和首次准备成本，固定模型质量、请求到达、图模式与其他开关。

最终部署指标优先是相同延迟约束下的有效吞吐，并报告 TTFT/ITL/p95 与输出质量。具体延迟约束在请求基线出来后、A/B 运行前固定。若目标子图只占很小的关键路径，局部加速未必值得集成；在固定其余工作且无重叠变化的近似下，可用 `1/((1-f)+f/s)` 做收益上限预估，不当作实测端到端收益。

本轮之后计划只保留一次目标明确的确认性 GPU 窗口，用于冻结 policy 的独立形状与已完成接入的对照；若 BF16 接口/正确性未完成，不为了赶进度宣称端到端优化已经成立。失败按数值、执行身份、模型选择、资源机制或应用覆盖归档，各自限定下一项修复。

## 8. 开机前交付清单

下一项本地工作优先次序：

1. 多候选进程运行器、退出/回收保护和预算 smoke 估计。
2. 一份固定 vLLM/模型资产清单及 EP8/BF16 启动方案，真实 router hook 和记录守恒测试。
3. 目标 rank 固定工作量的争用诊断、有限 trace 入口；原始 timing 与 trace 输出分目录。
4. 候选身份、输入哈希、重复次序、判定表和封存清单。

这四项完成才给出“可开机”交付。现在不再追加优化器轮次或新模拟场景作为开机前无限门槛。
