C 探索性但按三对规则或同进程对照；D 单进程探索。

## 2. 研究问题和三条路径

问题：expert-parallel 的 MoE 推理里，expert 第一个投影（gate/up）的输入行在别的 GPU 上，怎样把行交给 GEMM 最快。

- **All-to-All staging**：一次集合通信把行送到本地，再算。两个基线都属于这一类：网格上的调优 staged 路径（`SLT`，
  All-to-All 加调优的合并 cuBLASLt GEMM），快照上的原生路径（`NATIVE`，vLLM 的 all-gather 加调优过的原生 kernel）。
- **就地读**：GEMM 在主循环里直接读对端内存。两种写法：已登记的逐源消费者（每个源一次启动）；一次启动覆盖所有源、
  按行偏移表寻址的消费者。
- **拉取**：发布 barrier 之后，本地一个拷贝 kernel 把每一行从对端内存读一次，写到本地，再跑本地 GEMM。

对端路径都带两次 barrier（发布、释放），计入墙钟。

## 4. 第一次研究（节点 A，已登记）

**臂。** 逐源直读消费者：Triton kernel，64×256 的输出 tile，K 块 32，FP32 累加，每个源启动一次；q=4 时写四份 FP32 部分和、
另一个 kernel 合并。对照：同一个消费者跑在 All-to-All 送来的行上（匹配消费者比较）；调优 staged 路径；快照上的原生路径。

**网格（三对规则，3% 带）。**

| 模型 | 比较 | 直读赢 | 平或未定 | staged 赢 |
|---|---|---|---|---|
| GLM | 匹配消费者 q=1 / q=4 | 1–16 / 1–16 | 32 / 无 | 64–1024 / 32–1024 |
| Qwen3.5 | 匹配消费者 q=1 / q=4 | 1,4,16 / 1–32 | 2,8,32–128 / 64 | 256–1024 / 128–1024 |
| DSV2-Lite | 匹配消费者 q=1 / q=4 | 2–16 / 1–8 | 1,32 / 16 | 64–1024 / 32–1024 |
| 三个模型 | 对调优 staged，q=1 和 q=4 | 无 | DSV2-Lite q=4 的 M=1 | 其余全部 |

- 匹配消费者 q=4：直读在小 M 上快 6–22%；M=1024 时 staged 快 3.3–5.0 倍。
- 对调优 staged（q=4）：M=1 时基线快 1.1–1.2 倍，M=1024 时快 5–10 倍；q=1 时处处 2.4 倍以上。

**快照。** 直读对同一个消费者的 staged 版本：decode 快 7–15%，prefill 慢 2–4 倍。对原生路径（q=4）：decode 慢 1.6–2.4 倍，
prefill 慢 3.2–5.0 倍。六个都输。

**阶段时间（GLM，q=4）。** All-to-All 在 M≤64 约 0.11 ms，M=1024 是 0.28 ms。直读的发布 barrier 0.03 ms，释放 barrier 给墙钟
加 0.02 ms。M=1024 时逐源启动在对端行上是 7.4 ms，在 staged 行上是 1.1 ms（同一个 kernel、同样的数据），调优的合并 GEMM 是 0.43 ms。

**预测得分。**
- 开机前参数：调优 staged 处处赢，对；匹配消费者由直读转 staged，方向对；q=4 的实测区间在预测区间内（GLM、Qwen3.5）
  或重叠（DSV2-Lite）；q=1 预测 4–16，实测 16–64、16–256、16–64，不相交。
- 节点标定参数：预测小 M 持平、往上 staged 赢，没有交叉，失误。原因之一可以查实：它给直读加了两次 barrier、每次 45 µs
  （单独测的），合计 90 µs，接近 All-to-All 拟合的 97 µs 延迟；而在迭代内两次 barrier 合计只加了约 44 µs。
- 用 16 字节的七 peer 带宽离线重跑冻结的标定和预测（节点 B 的数），交叉点表不变。所以标定版的失误不是窄读探针造成的。

**上机时的两处改动（都在任何计时之前）。** 硬件 gate 加了一条规则：节点 A 的 GPU 在负载下满 400 W、时钟 1215–1245 MHz，
低于 1275 MHz 的阈值，唯一原因是软件功率上限，而 400 W 既是默认也是最大限额，接受。冒烟测试查出四处代码问题并修复：
容器主机名、对称内存后端的重复设置、快照准入里的类型转换、准入前给输出缓冲填 NaN。

## 5. 诊断：逐源消费者为什么输（探索）

1. **小 M 上是启动次数。** M=1 时逐源消费者的 GEMM 阶段 0.18 ms（q=4 每次迭代 16 个 kernel）；一次启动的消费者 0.04 ms；
   调优基线的合并 GEMM 0.06 ms。
2. **大 M 上是重复读。** 每个输出 tile 列都要重新请求远端行，重读次数 ρ：GLM 12，Qwen3.5 4，DSV2-Lite 11（tile 宽 256 列）。
   GLM 的 M=1024：需要 29 MB 的远端行，请求了 352 MB。
3. **所有卡按相同顺序读源。** 探针（每对 8 MiB，16 字节读）：七个 kernel 相同顺序 81 GB/s，按卡轮转 164 GB/s，一个 kernel 同时读
   七个 peer 193 GB/s；七张卡同时读一个源时每个读者 32 GB/s。
4. **消费者本身比库慢。** 在 staged 行上，逐源的 Triton 启动 1.1 ms，合并的 cuBLASLt GEMM 0.43 ms（M=1024）。

**读的宽度。** 已登记微基准的单 peer kernel 把对端缓冲当参数传入，编译出 16 字节读；七 peer kernel 从指针表取地址，编译器证明
不了对齐，编译出每线程每步 8 条 2 字节读。把地址改成"相对同一个基址、以 16 个元素为单位的偏移"后是 16 字节读。节点 B：

| CTA 数 | 单 peer | 七 peer，2 字节 | 七 peer，16 字节 |
|---|---|---|---|
| 约 28 | 44.8 | 24.3 | 45.6 |
| 约 56 | 85.3 | 24.7 | 86.3 |
| 约 112 | 151.0 | 24.3 | 150.1 |
| 约 224 | 200.4 | 23.6 | 194.4 |
| 约 448 | 200.4 | 23.7 | 182.9 |

（GB/s，每卡。）尺寸扫描：64 KiB 时两种读法都是 23 µs（一次 graph 启动的开销），2 MiB 是 99 对 27 µs，8 MiB 是 338 对 53 µs。

**要分清的一点。** 已登记的逐源消费者本来就是 16 字节读，它输不是因为读宽度。读宽度影响的是：微基准的七 peer 数字、
11-26 的所有一次启动臂，以及 11-26 的拉取（`PULL_SLT`）。也就是说它挡住的是替代方案，不是原设计。

## 7. 运行偏差（第二次研究）

1. 队列第一次启动因 `queue.csv` 是 CRLF 换行，在参数解析处退出，没有进程计时。改换行后重启（`f46b5ff`），预期文件没动。

3. 队列运行期间，CPU 节点上的脚本每 30 秒登录一次 GPU 节点查文件，我约每 10 分钟登录一次。
4. 筛选的第一遍网格（`-sweep`）与模型传输同时进行（低优先级 rsync）；第二遍和快照的两遍在传输结束之后。

## 9. 不能写、或要带限定写的

- "直读比 staged 快 1.69–3.16 倍"：只在 CUTLASS 研究的口径下成立（对手是逐对 NCCL 传输加合并 GEMM，K=8192）。论文里已降为
  背景，并说明不能读作对端读的优势。
- "对端路径在所有行数上都赢"、"M=1024 持平"：M=1024 整行拉取没有胜者，其中只有 DSV2-Lite 判平，GLM、Qwen3.5 未判定；
  整块拉取赢 1.10 倍，但 GLM、DSV2-Lite 上没有事先预期。
- "第一次研究里逐源直读每格都输"：66 格里 65 格判输，DSV2-Lite q=4 的 M=1 未判定。
- "按 prefill/decode 就能选路"：不成立。Qwen3.5 的 prefill 上大 tile 就地读比拉取快 1.37 倍。选路要看每对行数、重读次数和 tile。
- "原因是读宽度"：对微基准的七 peer 数字和拉取成立；对已登记消费者的失败不成立。三对规则的消融没做。
- "换层、换机型、端到端也成立"：没有数据。只测了每个模型的一层、一步，第一个投影，一种 GPU。
- "预期是盲预测"：不是。臂和配置是探索挑出来的，预期来自同一节点上的筛选。它保证的是结果没有事后挑选、跨进程和 seed 稳定。
- "预测模型能定位切换点"：第二次研究没有预测模型；就地读与拉取的切换点是测出来的。

## 13. 11-28 审阅后补充的事实

这一节来自对论文和数据的一次外部审阅，每一条我都对照代码或数据核过。

1. **准入检查的边界。** 准入前只把输出缓冲填成 NaN，中间缓冲不填。在网格上，拉取臂的行缓冲在准入时已经被算参考值的那次
   All-to-All 写成了正确的行，所以网格上的准入只证明 GEMM 输出对，不单独证明拷贝 kernel 搬了行；拉取臂的源顺序检查也是在
   All-to-All 上做的（`balanced.py` 的 `admit`）。在快照上，整行拷贝 kernel 是第一个写它那块缓冲的（准入按臂的列表顺序，
   `PULL_BLAS_R` 在 `BNEW_BLAS_R` 之前），所以快照上的准入覆盖了拷贝。整块拷贝（`PULLR_SLT`）只在网格上跑，没有这样的检查。
   旁证：拉取的传输时间随字节数增长，M=1024 时到链路带宽。
2. **原生路径的配置。** 快照回放用的是采集时记录的 kernel 配置，也就是节点 A 调优选出的。节点 B 重新调优后，在快照用到的
   两个批大小（32 和 16384）上选出的配置与它完全相同（本机 45 份回执逐一比对）。两台机器的调优文件在别的批大小上有差别。
3. **计时边界。** 迭代开始时激活已经在对端可见的内存里，把激活写进去的开销不在计时内；计到 gate/up 输出完成为止。
4. **没有事先预期、但按三对规则判定的快照比较。** 小 tile 就地读对拉取：三个 decode 都判赢（1.08、1.30、1.23）。
   大 tile 就地读对拉取：Qwen3.5 prefill 判赢（1.37），GLM、DSV2-Lite prefill 判输（0.89、0.84）。
5. **严格核对脚本。** `experiments/2026-11-27-confirm/verify.py` 把 234 个输出逐个绑定到 `queue.csv` 和 `arms.json`：
   单元、顺序、seed、臂列表、计时策略、准入、graph 启动、测试程序哈希。当前结果 0 个问题。`judge.py` 仍按文件名配对。
6. **最接近的相关工作**（已核实出处）：NVLinkOneSided（arXiv 2611.13188，dispatch 是推，combine 是拉）、GC-MoE
   （arXiv 2611.04222，独立的 dispatch kernel 把远端 token 拉进本地环形缓冲）、DeepGEMM 的 Mega MoE、NCCL EP
   （arXiv 2603.13606）。它们的评测都在 Hopper 或 Blackwell 上，比较的是整层。拉取这个想法不是我们的新东西；
   我们加的是 Ampere 上 GEMM 对齐的测量。
7. **数据在哪。** 第二次研究每个进程的输出在仓库里（进程级：每个臂的中位数、阶段时间、准入记录）；它的测试程序没有保存
   每次迭代的样本，所以这一级数据不存在。第一次研究的整个运行目录（234 个进程、每次迭代的样本、准入和日志）已于 11-28
   放进仓库 `experiments/2026-11-26-run/`，`reproduce.sh` 从它重算出的 `paper_results.json` 与论文用的逐字节相同。
