真实 MoE 采集器：本地准备与验收
日期：2026-11-17

本轮范围
用户已同意按 2026-11-17 的八卡 A100 方案进行本地准备。没有开 GPU、租 CPU、创建存储或下载模型、tokenizer、镜像。只读取了官方 vLLM 的少量源文件以核对采集位置和接口。预测器、参数、候选实现、六个冻结形状均不参与本轮修改/训练。

新增入口
EDM-IR/tools/build_real_moe_corpus.py：生成并冻结受控请求文本与测量顺序。
EDM-IR/tools/prepare_real_moe.py：将来在固定的远端 CPU 镜像里检查已有资产、生成精确 token IDs、核对引擎 API/依赖/源文件及 Nsight 工具；没有下载逻辑。
EDM-IR/tools/run_real_moe.py：默认只做文本/计划检查；baseline、routes、trace 三种模式。真正运行必须显式 --execute，并持有成功的 CPU 回执、固定资产和新的实例预算/平台自动删除回执。
EDM-IR/tools/analyze_real_moe.py：本地性能、路由和 Nsight SQLite 分析。没有预测器导入或拟合。

本地已实现
1. 128 条受控任务文本：中文 43、英文 43、代码 42；任务说明在上下文前，模板与截断规则固定。它们是为实验编写的结构化自然语言/代码任务，不是假称采自真实用户的生产流量。C1 取前 32 条，C32 取 128 条，三次重复复用原文本；两组同时存在请求数/内容子集和启动排空差异，不能把对比写成纯并发因果效果。
2. 12 个正式测量块的顺序冻结，总 960 请求。客户端闭环限流、完整输出 token/事件时间戳、失败/超时、部分完成回执和低频 GPU/引擎指标入口已接通。
3. 路由按真实来源切片。AgRs 先 gather 后 routing 时，仅将本 rank 对应片段搬回 CPU，不在八张卡上重复复制全部结果。dummy、padding 和真实 token 分离；记录执行步、层、rank、token 身份、prefill/decode/mixed。
4. 使用实际 Triton backend 的排序/分配与 padding 元数据核对专家行数，保留真实张量 shape/stride/dtype 和 kernel 配置。只复制本卡专家块；未识别路径保留原始几何及失败，不伪造 M_kernel。
5. 路由诊断启用 eager 和同步调度，并额外使用 CPU collective 对齐步骤；其耗时不能作为正式性能。baseline 使用原生 worker 和 Graph 配置。trace 保留 Graph 并使用 NVTX/短时 Nsight 窗口；没有 GPU 张量导出和诊断同步。
6. 按同一 rank/时间域计算区间并集和交集；未知 kernel 不自动归为计算或通信。Nsight 进程/rank 和 kernel 分类要有实际证据。不同窗口或 eager/Graph 的结果不混合。
7. 采集器绑定 vLLM 0.20.1 的官方源文件哈希；实际镜像不一致时拒绝使用这套钩子。不是依赖一个同名版本号就放行。
