# W1 八卡算子：本地分析与问题归因

日期：2026-11-11。数据来源：`../2026-11-11-shadeform-w1/recovered/`。

这轮已确认四个开发形状存在可观的候选优化空间，也定位到一项可以在本地复现的数值问题。尚不能宣布预测器通过验收：历史评分只覆盖部分候选，执行条件发生变化，而且本轮四个形状的最优候选都属于 fused，没有提供最优路径为 host 的反向选择证据。

只分析原四个开发形状，未读取六个冻结形状的数据，未训练或修改评分模型，未启动 GPU、云实例或日志中心。以下“最佳”均指本轮测过、通过三个种子检查的候选；不能理解为所有实现中的理论最优。

## 1. 数据口径和可复核性

- 129 个回收文件逐一通过 SHA256/长度校验；207 个封存源码文件通过校验。
- 30/30 个进程组完成，原始 stdout 与解析行一致，构建、运行环境和输入身份一致。
- 168 条正确性检查；24 条失败记录，涉及 10 个形状×候选组合。任一检查种子失败，该组合的所有计时均不可参与排序。
- 46 个合法组合：42 个主矩阵组合、4 个流水配对组合。每个组合三次进程重复，共 138 行、13,800 个原始时间样本。pilot 不计入。
- 正确性种子为 20261020、20261101、20261102；计时只使用 20261020。这是三个计时进程重复，不是三个计时输入种子。
- 中心耗时是“三个进程中位数的中位数”。每进程预热 20 次、测量 100 次。保留全部样本，不将 300 个样本视为 300 次独立环境试验。
- 计时覆盖单个 CPU 进程对八卡执行 `backend.execute()` 和 `backend.synchronize()`，包含提交、依赖处理及同步开销。它不是单个 GEMM 的纯设备时间。
- 输入已完成上传、固定且不变；metadata 已准备。主测试不包含 profiler/NVTX。不能据此直接外推动态输入、BF16 或真实 serving。

硬件为 8×A100 SXM4 80 GB、全对全 NV12/P2P 可达；CUDA runtime 12.8、实际加载 NCCL 2.28.9。环境字符串中还保留旧的 `NCCL_VERSION=2.25.1-1`，它不代表实际加载库；以后记录应明确区分环境变量与 runtime 查询/库哈希。

机器可读结果在 [analysis.json](analysis.json)，完整候选表在 [TABLES.md](TABLES.md)。脚本对缺失进程、混合环境、错误候选或不完整正确性种子直接报错，不输出部分完成的“成功”结果。

## 2. 四点的实际收益：这是事后最佳候选，不是预测器收益

形状按照 `(P,M,K,N)` 保存，下面为方便阅读另列 M、K、N。耗时单位为 ms。

|开发形状|M / K / N|本轮最快合法 fused|fused 中心耗时|本轮较快合并 host|host 中心耗时|host / fused|耗时缩短|
|---|---|---|---:|---|---:|---:|---:|
|grouped|64 / 8192 / 1024|q8/g2|0.595975|cuBLASLt|1.138725|1.91×|47.66%|
|M512|512 / 8192 / 512|q4/g2|0.934276|CUTLASS|2.876246|3.08×|67.52%|
|大 N|64 / 4096 / 2048|q2/g1|0.589496|CUTLASS|1.026022|1.74×|42.55%|
|M256|256 / 8192 / 512|q8/g2|0.702721|CUTLASS|1.868752|2.66×|62.40%|

这些收益不依赖只挑最弱的 per-source host：该 host 本身比本轮较快的合并 host 慢约 1.78–2.32 倍。用它作唯一基线会明显放大收益。即使逐轮选当轮较快的两个合并 host，表中 fused 选择在每轮仍有约 41%–68% 的耗时优势。

但两个合并 host 的通信层仍使用相同的逐对 send/recv：P=8 时每次执行有 56 个远端 NCCL group 和 8 个本地 copy，随后每个目的卡执行一个合并 GEMM；cuBLASLt 选择一个启发式算法，没有性能搜索。这比原 per-source GEMM 基线更充分，仍不等于对最优批量通信、成熟 MoE dispatch 或整个推理引擎的比较。当前大幅收益不能全归因于 tile，也不能写成相对 DeepEP/vLLM 的加速。

三轮 cuBLASLt 算法身份各自保持一致。M256 的 host 计时变化不能直接解释成“cuBLASLt 换算法”。

## 3. grouped-N 与 split-K 的耦合已被三轮数据直接支持

下表为同一进程内 g2 相对 g1 的耗时缩短范围；负值表示 g2 更慢。q、形状保持相同，只改变 g 对应的内核配置。

|形状|q1|q2|q4|q8|
|---|---:|---:|---:|---:|
|grouped|−20.38%～−19.23%|−13.33%～−13.21%|−4.13%～−1.21%|+7.30%～+9.79%|
|M512|+0.50%～+6.08%|+29.30%～+30.45%|+39.67%～+43.69%|数值不合格|
|大 N|−15.92%～−15.68%|−4.61%～−0.03%|−2.84%～−0.26%|+6.24%～+10.84%|
|M256|−12.81%～−12.53%|−7.33%～−7.26%|+21.22%～+21.30%|+28.52%～+28.80%|

因此，把 grouped-N 表达成固定收益项不成立；把 split-K 表达成始终改善并行度也不成立。例如 M256 的 g1 从 q4 到 q8 反而变慢，而 g2 的 q8 仍略快于 q4。

这里的 g2 在封存代码中具体是 CTA tile 从 `64×128×32` 改为 `64×256×32`，warp tile 保持 `32×64`，对应每 CTA 从 4 个 warp 变为 8 个。它同时改变 A 复用、CTA 数量、每 CTA 资源与任务长度，不能把所有差异都叫作“减少通信量”。

可计算的数量为：每个 GEMM 的 CTA 数 `ceil(M/64) × ceil(N/(128g)) × q`；本轮 K 都能被 `32q` 整除，每片 K 深度为 `K/q`。例如 M512、q4：g1 为 128 个 CTA，g2 为 64 个 CTA，却是后者明显更快。**仅用 CTA 数相对 108 个 SM 的比例解释性能是不够的**；还要描述每 CTA 的工作量、warp/资源配置、远端读取和串行归并。CTA 数不等于实测活跃 SM 数，缺 trace/counter 时不报 occupancy 的测量结论。

四点不是一个正交网格：grouped 与大 N 同时改变 K、N；与 M256/M512 比又同时改变 M、N。M256→M512 则保持 P、K、N 不变、M 翻倍。应保留这些共同变化，避免从四点拟合一个普遍的 M 阈值。

## 4. 数值失败：已在本地复现 M512 的分片舍入机制

封存实现为 CUTLASS `SplitKSerial=true`，片内 accumulator 是 FP32，但输出 D 是 FP16。后续 K 分片以 D 为 source，等到前一片的 semaphore 后，做 FP32 加法并再次转换成 FP16：

`D_i = FP16(FP32_dot(A_i, B_i) + FP32(D_(i-1)))`。

q 增大同时增加了中间结果舍入次数、D 的读写及串行归并依赖；这些不能从纯 FLOPs 恒等式中消除。

用同一份已校验的 M512、seed=20261101 输入，在本地 CPU 完整重放 64 个 source/destination 对、16,777,216 个输出。FP32 分片和与原 CPU reference 逐元素一致，差值最大为 0。结果见 [完整算术复核](rounding-full-m512-seed20261101.json)：

|q|本地最大绝对误差|本地最大缩放误差|本地超限元素数|与 GPU 记录|
|---|---:|---:|---:|---|
|1|0.015625|0.000488043|0|记录精度内一致|
|2|0.0224609375|0.0078125|0|记录精度内一致|
|4|0.0283203125|0.0146484375|0|记录精度内一致|
|8|0.0458984375|0.0205078125|1|g1/g2 的两个最大误差均精确一致|
|16|0.05859375|0.02734375|38|g1/g2 的两个最大误差均精确一致|

误差上限实际定义为 `max_i |actual_i-reference_i| / max(1, |reference_i|) ≤ 0.02`。源码还判断最大绝对误差≤0.02，但由于缩放误差不大于绝对误差，该分支不改变最终通过集合。它不是标准 `atol + rtol*|reference|` 的逐元素 allclose；字段名 `max_rel_error` 应解释为带分母下限的缩放误差。

这个复核强力支持 M512 的 q8/q16 失败源于多次 FP16 回写，而非先假设网络同步随机损坏。CPU 重放的超限数量是本地算出的；GPU 原记录只保存汇总最大误差，没有逐元素输出，不能声称 GPU 的超限位置和数量已被直接核对。其他形状仍保留原 GPU 失败，未逐个重放。

本地 q8 唯一超限位置为 source=6、destination=5、row=312、column=400（均从 0 计数），reference=0.0595703125，模拟结果=0.0390625。输入生成器按矩阵坐标和流编号确定数值；同一种子下 M256 的各输入是 M512 的前 256 行、权重相同。row=312 不在 M256 的输出范围内。这解释了为何本例 M512 检出 q8 失败而 M256 没检出：它首先是更多输出暴露了舍入极值，不应直接归因于 M512 的性能表达或并行度模型。

抽样复核的 262,144 个输出一个都没超限，完整重放才找到 q8 的 1 个超限点。这说明少量抽样正确性检查可能漏掉这类边界错误。两份记录都保留。

在这个输入上，跨片保留 FP32、最后只转一次 FP16，算术结果等于 q1 的输出舍入，最大缩放误差约 0.0488%。这提供明确修复方向，但不同归并方案会改变内存、同步与执行代价，必须有新的实现身份并重新测量；不能修改阈值后把旧 q8/q16 的时间标签重新放回来，也不能据此宣布 BF16 已验证。

记录细节：正确性成功行在第一个失败之前只输出 6 位有效数字；失败行把流精度设为 17，之后的成功行也变成 17 位。因此 g1/g2 原 JSON 的数值有表面差异，60/60 对在共同记录精度下相容，失败对的最大误差精确相同。后续采集应每行显式设置精度，不能把打印精度差当作算术差异。主计时行本来就使用 17 位，不受此问题影响。

## 5. 对旧评分的判断：不要混淆三类失败

上机前 `prior-predictions.json` 明确标为旧执行身份的 P8 留形状预测，56 个组合只有 20 个有分数；其中 M512 q8/g2 本轮不合格，剩余 19 个合法交集。全部 `w1_calibrated_prediction_us` 都是 null。本轮使用共享通信组和新的 prepared/immutable 执行条件，不能把跨条件的误差写成 W1 标定模型的精度。

|形状|原先最低预测耗时的候选|本轮判断|相对共同合法候选最优的损失|相对扩大后合法候选最优的损失|
|---|---|---|---:|---:|
|grouped|q8/g2|仍为汇总最优|0%|0%|
|M512|q8/g2|数值不合格；在其余已有分数候选中选 merged cuBLASLt|0.80%|210.31%|
|大 N|q4/g2|共同候选中 q4/g1 更快；新加入 q2/g1 更快|1.94%|2.69%|
|M256|q8/g1|旧共同候选内仍最快，但未评分的新 q8/g2 更快|0%|40.20%|

M512 的 210.31% 是“先套用本轮数值门槛，再只在旧评分覆盖集合内选择”的反事实损失，不是一次实际在线回退结果。M256 的 40.20% 同样暴露候选覆盖不足；不能拿未评分候选的缺失当作普通回归误差。大 N 才保留了可以在共同候选中直接观察的排序反转。

下一版应先有一致的候选集合和可用性判断，再比较同一执行身份下的分数。此时盲目增加模型参数、换优化器或调损失权重，会把数值、候选缺失和执行条件变化一起拟合进去。

## 6. 波动与流水收益：方向和精确幅度分开

- grouped 的逐轮冠军为 q8/g2、q8/g2、q4/g1。汇总选择 q8/g2 在第三轮相对当轮最快慢 0.90%。
- 大 N 的逐轮冠军为 q4/g1、q2/g1、q2/g1。汇总选择 q2/g1 在第一轮相对当轮最快慢 0.61%。
- M512、M256 的汇总冠军在三轮中均最快。M256 q8/g2 相对 q4/g2 的优势仅约 1.19%，应同时报告幅度。
- 138 个计时块中有 26 个的后 25 样本中位数相对前 25 样本变化超过 5%（仅作描述性检查，不据此过滤）。M512 流水第一轮下降约 16.02%，串行第二轮下降约 15.89%。固定 20 次预热没有保证所有块内无趋势。
- M256 两个合并 host 的三进程中位数范围分别约 17.45%、16.20%，而候选算法身份保持稳定。不能仅凭首尾 `nvidia-smi` 快照把原因确定为时钟、温度或平台争用。

流水与串行是同进程配对、改变先后顺序的独立阶段：

|形状|流水中心 ms|串行中心 ms|逐轮耗时缩短|中心值耗时缩短|
|---|---:|---:|---|---:|
|M512|4.358424|5.066429|13.97%、16.36%、10.33%|13.97%|
|大 N|1.715482|1.896946|7.09%、9.99%、9.79%|9.57%|

两种形状三轮都观测到流水比其串行对照快。但两者都是 per-source 执行，不能把改善扩大为“流水优于合并 host”；当前描述性对比恰恰显示合并 host 更快。配对仍为顺序执行，块内漂移会影响精确幅度。4 份 trace 尚未采到，所以现在只能报告程序净耗时差，不能宣称这些百分比就是通信被隐藏的比例。

## 7. 已收敛的修改顺序与新增证据边界

1. **先修数值可用性表达。** 候选身份补齐输入/输出 dtype、片内与片间 accumulator、归并方式、精度契约。保留 q8/q16 的失败记录；设计 FP32 跨片归并候选，CPU 可先验证算术正确性，GPU 后续只验证新内核的正确性与代价。
2. **再修评分接口的覆盖和执行条件。** 统一当前 56 个已注册组合的“有分数/无分数/数值不可用”状态；明确共享通信组、host 调用分组、prepared metadata、输入 ready 条件等身份。不同身份不无条件混合标定。本轮未训练；先验收候选完整性再做新的留形状评估。
3. **聚焦 q×g×并行度与归并深度。** 加入可计算的 tile/warp 数、K 分片深度、FP16 回写次数及对应内核资源信息。不要硬编码 M512 或大 N 修补规则，不从本轮四点直接拟合普遍边界。
4. **测量包先补轻量机制证据，再扩大数据。** 下一次保留原四份 trace（grouped q8/g1、q8/g2；M512 流水、串行），与不带 profiler 的主计时分开。围绕 grouped 的 q4/g1↔q8/g2、大 N 的 q2/g1↔q4/g1↔q4/g2 做短交替复测并记录块内趋势，不能事后删除慢样本。NCCL 批量分组优化应成为独立的新 host 基线身份，先本地实现和检查，再测量。
5. **泛化和应用证据最后验收。** 六个冻结形状继续保持未读，待可用性、评分输入和执行条件锁定后一次性评估，检查 host/fused 双向选择。真实 MoE 还需要 BF16 算子契约、专家 token/维度/频率分布和端到端指标。本轮四点都以 fused 为优，无法代替这两项。

这轮已具备“性能差异、数值机制、旧评分覆盖问题”的证据；还欠“共享资源与 overlap 的直接时间线、同身份完整候选评分、冻结形状以及真实应用”。后续无需继续无差别重采四点全矩阵。

## 8. 复现

只需要本地 Python；主统计使用标准库，不会连接服务器。CPU 算术诊断使用已缓存的 NumPy 2.0.2，工作量固定为一个已测开发输入，不做参数优化。

```sh

PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s experiments/2026-11-11-w1-local-analysis -p 'test_*.py' -v
```

`analyze.py` 需要 Python ≥3.11（使用 `hashlib.file_digest`）。六项统计/准入检查已通过；另有全量数据一致性校验和 CPU 对原 reference 的逐元素校验。可通过 `--bundle`、`--run`、`--prior` 指定封存包和数据路径。
