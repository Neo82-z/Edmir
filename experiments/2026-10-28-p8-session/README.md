## 失败究竟是什么

完整原矩阵先得到 7 条有效记录，随后 `M64/K4096/N2048, q16/g1` 的初次数值检查失败，流程停止。这批不完整记录保留在 `recovered/work/shape5-01/`，不并入子集三轮统计。另两个 q16/g2 配置分别在 K8192/M64 和 K8192/M512 上三次失败，全部保留，未补造耗时。

对首个 q16/g1 另编译了仅增加错误输出的诊断程序，内核、输入、容差均未改；三次独立进程得到相同的误差证据：

- 最大绝对误差 0.0458984375；最大归一化误差 0.0205078125，阈值为 0.02，无非有限输出。
- 第 14 个 source/destination 输出块，行 56、列 864：FP32 参考为 0.8623046875，GPU 为 0.841796875。
- 使用原输入在本地进行精确分区求和，再模拟每次 serial split-K epilogue 写回 FP16，**逐值复现 GPU 的 0.841796875**。三个诊断重复均匹配。

因此，这个失败点存在足以触发阈值的 FP16 串行舍入累积机制，无需用同步故障解释这个反例。它不是随机性能波动，也不是损失函数选错。这个单元素复现不能排除其他输出上的问题，另两个失败形状也还没有逐元素复现，不能笼统宣布所有 q16 失败都已定位。当前检查是全局最大误差条件，归一化分母为 max(|reference|,1)，不是常见的加法 atol+rtol 判据；本轮保持原判据不变。

首次诊断调用误用了 0/1 次预热和计时，被 CLI 的 20/100 下限拒绝，未执行 GPU 数值检查；这三条调用错误与修正参数后的三个真实诊断分开保存，不计为额外的数值失败。

## 范围与执行身份

原冻结包是 8 个形状、117 配置、351 次进程。现场确认每个进程有十余秒初始化及清理开销，无法在本轮费用窗口跑完整矩阵。因此另建 `subset-plan.json`，选取此前四点设计中的形状，以及原候选池中的固定 q/g 对照，缩减为 22 配置；子集开始后没有根据耗时增删候选。该清单是本轮运行中形成的预算调整，**不是原完整计划或独立预注册实验**。

机器为 8×A100-SXM4-80GB，全部 GPU 对之间 NV12/P2P；CUDA 12.8、NCCL 2.28.9-1，CUTLASS/NCCL 源码提交与原包一致。输入与 FP32 参考在服务器重建，8 组文件的字节哈希全部匹配原包。fused 使用 `uniform_immutable_peer_v1`；测量是主机 steady_clock 包围 execute+synchronize。未启用 profiler/NVTX，服务器无 nsys，因此没有新增组件时间或通信重叠的因果分解。

服务器原 CMake 3.22.1 未传递 CUDA C++20 标志，首次编译失败；升级官方包至 CMake 3.30.5 后构建成功，101 份程序和 103 项 host/layout 测试通过。测试通过不等于所有 GPU 数值候选通过。主仓库另加入 `CUDA_STANDARD_REQUIRED ON`，以后不支持该标准时在配置阶段报错；本轮冻结源码未改。
