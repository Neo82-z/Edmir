vLLM 推进边界（2026-11-14）

不以评分器零误选为前提
现在可以准备原生 vLLM 推理和真实路由采集。本轮八卡算子窗口用于核实 FP32 归并、同条件候选耗时及 large-N/M256 的执行证据；这些结果会决定如何接入本方法，不应阻止原生引擎先提供应用数据。
目标是在本轮之后的下一次 GPU 窗口运行原生推理与真实专家负载采集。这个目标仍需要完成下列本地准备，当前不能说入口已经实现或权重已经就绪。下一窗口需单独约定预算，本轮授权仅为 Shadeform 最多 $15、最长一小时。

第一条原生推理与论文的正式应用实验是两个验收点
第一条原生推理：固定模型 revision、引擎与 tokenizer，实际生成非空输出，记录加载、预热和首次运行状态。此项不要求我们替换算子，也不要求八卡才有意义。
正式应用数据：验证实际 EP/TP 配置和八个参与 rank，记录每层每步的专家 token 数、投影维度、频率及请求负载；端到端基线与路由采集分别运行，避免 instrumentation 污染计时。
方法加速：在相同引擎、请求、精度与正确性合同下，比较原生路径、固定策略、本方法冻结策略。必须统计完整执行及必要的数据变换，不得用单算子加速代替端到端加速。

目前已核实的缺口
1. EDM-IR/tools/profile_moe_shapes.py 目前只汇总已提供的 router envelope，不执行模型；实际 vLLM router 采集钩子尚未接通。
2. 旧 RunPod 权重缓存已删除，只有 revision、文件摘要和软件锁定记录留在本地。必须提前重新准备一个模型，不能让八卡空等数十 GB 权重下载。
3. 历史引擎锁定为 vLLM 0.20.1 / PyTorch 2.11.0 / CUDA 13.0.2；本轮算子是 CUDA 12.8。两个环境分开准备，部署时检查驱动兼容性，不能混为同一执行身份。
4. 新融合实现仍是 FP16 输入、FP32 跨片归并、最终 FP16 转换。运行时已有部分 BF16 类型映射，但数值验证工具与当前候选实现并未完成 BF16 正确性闭环。
5. 固定输入微基准不能证明真实调用安全。接入前须验证变化输入、异步完成依赖、路由重排、专家投影/激活/组合及完整层输出与 logits。

本地准备的固定顺序
A. 先完成本轮 CUDA 编译、CPU 检查和可搬运执行包，保留失败与构建回执；六个冻结形状保持封存。
B. 原生 vLLM 准备只选一个模型。优先检查既有 GLM-4.7-Flash 固定 revision 的架构支持、BF16 和 tokenizer 一致性；确认后再下载，不同时准备多个大权重。模型选择、精度和并行度写入运行清单。
C. 实现实际 router 输出到已有 envelope 的适配，在小样本上核验层、步、rank、token 数与 top-k 守恒；重算/重复统计和 padding 必须明确。该模式只采分布，不作为性能标签。
D. 固定一份请求清单、种子、输入输出长度、预热与重复规则，原生性能模式关闭路由记录。保存实际输出 token 数及有效吞吐、TTFT/TPOT/延迟分位数，计入失败请求。
E. 本轮结果回本地分析后，决定合法候选及 BF16 实现；并行准备完整 MoE 层替换。先过正确性再评估性能，不为获得正结果删除失败案例。
