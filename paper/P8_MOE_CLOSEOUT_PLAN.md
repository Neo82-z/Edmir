# 八卡真实 MoE 收尾方案

**2026-10-28 增补：**已实现真实 router 输出的[形状统计接口与规则](../experiments/2026-10-28-shape-evaluation/README.md#真实-moe-的统计接口)，分别记录逐源专家 M、合并专家 M、逻辑 K/N、出现频率和实际后端 padding。原 P8 已测形状与新计划集合分别计算覆盖，FLOPs 覆盖不能解释成时间覆盖。尚无真实 trace；引擎 hook 与实际执行仍待验证。本增补不增加模型或工作负载。

2026-10-25，协议版本 `p8-moe-closeout-v1`，状态：范围已确定，资产和 GPU 接入尚未完成，正式采集清单尚未封存。A3B 选型复核后，优先准备对象由 35B 调整为 Qwen3-Next-80B-A3B-Instruct；这是替换主模型，不增加第二套实验。

用户决定：完成当前八卡算子验证后，必须进入八卡真实 MoE 推理实验；模型与引擎在无 GPU 计费阶段提前准备。随后整理证据、修改论文并收尾，停止开放式扩展。MoE 的本地准备与当前算子验证并行，正式计时依次执行，避免共享 GPU 干扰。

本方案新增完整推理验证，并收紧早期 D7 的广泛实验安排；旧协议、原数据和未完成状态保留，不把它们改标成新协议结果。D7 的 route 记录、语义检查和统计代码可以复用，但原来仅到 expert-GEMM/combine-input 的边界不等于完整 MoE 层或完整模型。

## 1. 唯一的主实验对象

| 项目 | 本轮选择 |
|---|---|
| 硬件 | 单机 8×A100 SXM4 80GB，完整 NVLink/P2P；实测核对拓扑 |
| 模型 | 优先准备 `Qwen/Qwen3-Next-80B-A3B-Instruct`，真实 BF16 权重、纯文本输入；按下述记录锁定 revision，GPU EP8 兼容性待验收 |
| 引擎 | vLLM，一个固定版本/commit 与容器或依赖锁定清单 |
| 精度 | BF16 主路径；不把旧 FP16 标定标签并入 BF16 |
| 并行 | 明确启用 EP=8；准备目标为 TP=1、DP=8，实际专家映射和通信组必须验证 |
| 对照 | 同一引擎提交与依赖下的原生基线、启用本方法的版本；其余执行设置保持一致 |
| 正式负载 | 输入长度 512 / 4096 token × 并发 1 / 128，共 4 个点；输出固定预算 128 token。原高并发 16 调整为 128 以避免仅覆盖极稀疏 decode；不增加矩阵维度，实际每步 token 与 expert M 另记录 |
| 重复 | 每版本每负载 3 个独立计时区组，共 24 个主测量区组 |

每区组请求数固定为 `max(128,4×并发)`，即低并发 128 请求、高并发 512 请求，让高并发点有持续补充请求而非仅发出一批。两种实现复用同点完全相同的请求与顺序；prompt/tokenizer/请求顺序、采样方式、EOS 策略、预热和稳态窗口在计时前封存。输入长度以实际 tokenizer 后的 token 数为准；输出预算不冒充实际输出长度。若为固定工作量使用 ignore-EOS，明确作为 benchmark 设置记录。使用一份公开文本语料的固定子集；可复现生成请求与 token IDs，不以随机 route 代替真实路由。

这些负载是本轮预设的收尾矩阵，不是已经运行的结果或吞吐承诺。单区组超时、总运行时限及结果回收预留需要根据实际租用额度和小规模启动计时写入执行包；没有预算值时不能启动无界队列。模型 revision、引擎 commit/镜像 digest、语料 revision 仍待锁定，不能使用浮动 `main/latest` 作为论文身份。

vLLM 官方 Qwen3-Next 指南明确给出四卡 A100/A800 的 TP 部署支持；这是 A100 可运行性依据，不是我们的 TP1/DP8/EP8 已经通过。vLLM EP 文档定义 EP_SIZE=TP_SIZE×DP_SIZE 并提供通用 `allgather_reducescatter` 路径，因此以该路径作为准备对象。具体锁定版本的 BF16、EP8、图捕获和 MoE kernel 仍须验收；MTP 关闭。[模型官方页面](https://huggingface.co/Qwen/Qwen3-Next-80B-A3B-Instruct)、[A100 部署指南](https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3-Next.html)、[vLLM EP 文档](https://docs.vllm.ai/en/latest/serving/expert_parallel_deployment/)。

### A3B 选型依据与容量估计

核对官方 config、固定 revision 的权重索引及模型 API 后，记录在[选型元数据](../experiments/2026-10-25-moe-model-selection/comparison.json)。未下载大权重。准备 revision 为 `9c7f2fbe84465e40164a94cc16cd30b6999b0cc7`。

| 候选 | 每层 routed experts / top-k | 层数 | checkpoint 张量字节，十进制 GB | EP8 每卡 routed experts |
|---|---:|---:|---:|---:|
| Qwen3-30B-A3B-Instruct-2507 | 128 / 8 | 48 | 61.06 | 16 |
| Qwen3.5-35B-A3B | 256 / 8 | 40 | 71.90 | 32 |
| Qwen3.6-35B-A3B | 256 / 8 | 40 | 71.90 | 32 |
| Qwen3-Next-80B-A3B-Instruct | 512 / 10 | 48 | 162.65 | 64 |

这些是官方权重张量体积，不是整体运行显存。Next 的 routed 权重按 `2×48×512×3×2048×512` 字节计算，EP8 每卡约 19.33 GB；若 TP1 且其余 checkpoint 张量全部复制，每卡权重合计约 27.36 GB（25.48 GiB）。还须增加 KV/SSM 状态、激活、图、通信 workspace 和加载峰值。它在八卡 80GB 上有容量余量，但不应宣称必须八卡才能容纳，或一定能跑满八卡。

Next 与原 35B 模型的 hidden size 都是 2048、expert intermediate size 都是 512。增加的主要是专家池和层数，单 expert GEMM 并未变宽：gate/up 若合并是 K=2048、N=1024，down 是 K=512、N=2048；实际后端布局另核对。因此选择 Next 是为了纯文本、较大的专家池和明确的 A100 部署依据，不是预设它对我们的 split-K 更有利。Qwen3.6-35B 的主要几何与 3.5 相同，不能解决“规模小”的顾虑；其他多模态 80B-A3B 不额外纳入本轮。

均匀路由下，一次全局 MoE forward 有 T 个 token 时，平均每专家行数为 `T×top-k/E`。T=16 时，Next 仅为 0.3125 行，原 35B 为 0.5 行；T=128 时分别为 2.5 与 4 行；T=4096 时分别为 80 与 128 行。实际空专家、偏斜和来源分桶必须记录，client 并发不等于一次 forward 的 T。故将已有四点矩阵的高并发从 16 改为 128，仍保留低并发点，并以真实 scheduler token 数和路由分布解释运行结果。

## 2. 先无卡准备，再启动八卡

1. 先核对可提供单机八卡的区域与持久存储位置，再创建准备环境。CPU Pod + 同区域 network volume 是默认方案；这避免 GPU 计算费，但 CPU/存储仍有费用。Runpod 文档说明网络卷需在部署 Pod 时绑定，位置会限制可选 GPU，不能承诺把任意现有 Pod 原地变成八卡。[网络卷文档](https://docs.runpod.io/storage/network-volumes)、[CPU Pod 与网络卷支持](https://www.runpod.io/blog/enhanced-cpu-pods-docker-network)。
2. 在 Linux x86_64 无卡环境下载并校验唯一模型的固定 revision、config、tokenizer、权重索引及全部被引用权重分片；下载引擎固定源码/镜像或 wheelhouse，记录哈希。安装目标是后续 CUDA 引擎，不能误装 CPU-only PyTorch 来声称 GPU 环境已准备好。
3. 保存固定请求、计时脚本、分析脚本、基线/改进版本及补丁。能无卡完成的依赖解析、导入/静态检查、离线编译和 CPU 语义测试提前完成；GPU 驱动、NCCL、真实显存、kernel 加载、JIT 和 CUDA graph 预热仍需 GPU。
4. 所有资产放在持久卷或可恢复的镜像/制品中；容器临时目录里的安装不会自动随网络卷迁移。保存可重建环境，不默认搬运虚拟环境即可跨主机使用。
5. 权重完整、资产锁定、接入补丁和采集包就绪后才开八卡。启动先做环境/正确性/最小推理检查，再计时；结果分块回传本地，末尾校验原始数据和哈希。冷启动/权重加载耗时单列，不混入稳态 TTFT。

当前没有准备节点 SSH、持久卷位置或本轮额度，因此本次只更新本地方案，没有创建付费资源、下载大权重或启动推理。

## 3. 必须补齐的一条接入链

现有仓库已经有 routed CPU 参考、合成演练、记录格式和导出检查，尚无完成验收的真实 routed BF16 GPU harness。完整模型跑通本身不能证明本方法有效。

本轮接入只覆盖一个模型的一条 MoE 路径：真实 router/top-k → dispatch/重排 → 对应专家独立权重的 GEMM/激活 → down projection → combine → 后续层。K、N、专家数与放置从固定模型 config 和实际执行导出；gate/up 合并维度、各 expert 的实际 M 不能直接照搬均匀 proxy 的 M。

- 首先保留原生引擎作为可运行基线，再将本方法接到明确的同语义执行位置，输出实际调用次数/形状/候选决策记录。关闭或旁路该方法必须能恢复基线，不能只修改开关名称。
- 合成路由与真实 route 分开；不丢 token，不省略 gate、激活、combine 或 layout/metadata 转换来制造加速。专家独立权重和 BF16 数值检查不能由旧零输入 FP16 测试代替。
- 旧 `ScaleAwareModel` 只适用于归档均匀 FP16 程序，不能直接通过解除环境检查接收真实 BF16 模型。这里只迁移已审查的计数和选择思路；必要的映射、特征可用性及标定使用单独的真实路由开发请求，正式评价请求不参与调整。
- 收集 route/分层信息使用独立诊断窗口；正式基线/改进计时都关闭高开销记录。模型输入、并行度、调度、缓存与采样设置在对照间固定。
- CPU 可验证索引与统计，但 GPU 的 BF16 数值、跨卡同步和引擎兼容性需要启动后检查。预先规定层输出/最终 logits 的误差口径，生成文本的差异另行记录；不默认浮点路径更换后文本必须逐 token 相同。

收集“真实 trace 上的 MoE 层结果”和“完整模型结果”，前者解释收益来源，后者验证实际影响。若方法最终未进入完整推理路径，整模型结果只能标为原生引擎基线，不能填入“我们的端到端加速”栏。

## 4. 收尾只保留必要指标

| 层次 | 报告内容 |
|---|---|
| 正确性与执行 | 固定输入的数值误差、route 完整性、EP=8 实际通信与专家放置、方法调用覆盖 |
| MoE 层 | dispatch、专家计算、combine 与整体层时间；prefill/decode 分开；重叠阶段不直接相加 |
| 完整推理 | TTFT、TPOT/ITL 的明确口径及 p50/p95、请求端到端延迟、实际输出 token/s、失败/OOM |
| 选择开销 | 特征/选择/编译/预热与缓存复用；冷启动另列 |
| 统计与来源 | 3 个独立区组及配对请求、完整样本、源码/权重/环境/请求哈希 |

同一次真实推理内分别统计 prefill 与 decode，不再新增两套独立模型。有限诊断层的位置事先固定；其 trace 不计入整模型稳态性能数字。

## 5. 完成条件与范围终点

完成条件是：八卡算子验证已收束；唯一真实 MoE 模型完成基线与本方法的同口径八卡对照；正确性和数据来源可审阅；正收益、无收益或退步均如实解释；数据回收到本地并形成论文图表和复现包。**不把获得正加速比作为结束实验的条件。**

本轮不追加第二模型、第二引擎、其他 GPU、其他量化精度、P2/P4 的真实模型扩展、DBO/ubatch、PD 分离、长上下文或额外缓存实验。已有 P4 算子结果保留作机制对照。正式评价后只修复可复现的正确性/执行/测量缺陷并明确作废受影响区组；性能不理想不作为扩大矩阵、换模型或重训的理由。未能解决的性能问题归入论文限制。

下次上机前的交付是两个边界清楚的执行阶段：**八卡算子包 → 八卡真实 MoE 包**。无卡资产准备与本地接入工作提前并行，正式八卡采集后进入数据分析与成稿。
